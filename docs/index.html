The Problem

An accountability problem, not a notification problem.

Vulnerability scanners flood repositories with alerts, but without ownership or consequences, backlogs grow until an audit or incident forces a scramble.

Alerts accumulate

Dozens of Dependabot PRs sit unmerged. Upgrades compound in risk superlinearly, creating a strong incentive for engineers to avoid touching dependencies.

Unclear ownership

Security teams flag repositories, but developers don't know who owns which manifest. When everyone is responsible, nobody fixes it.

Zero consequences

Ignoring a critical advisory today is free. Pull requests continue merging, shipping new features on top of vulnerable components.

Architecture

Ownership → SLA → GitHub Check

Curfew evaluates debt purely at pull request time without background polling, daemons, or persistent databases.

1

Attributes each alert via CODEOWNERS

Curfew matches open Dependabot alerts against the repository's .github/CODEOWNERS file to identify the user owning that manifest. If no rule matches, it falls back transparently to the last commit author who touched the manifest.

2

Enforces severity-based SLAs with an install floor

Default windows: Critical (7 days) · High (30 days) · Medium (90 days) · Low (exempt). The clock starts when the alert is published, but never before Curfew was installed — preventing historic debt from blocking day-one PRs.

3

Gates only the PR author's overdue debt

When a PR is opened or synced, Curfew publishes a GitHub Check. It fails only if the author owns overdue debt in that repository. If configured as a required check in branch protection, overdue debt blocks the merge.

Walkthrough

María's debt never blocks Carlos

An illustrative everyday scenario in a monorepo showing how Curfew isolates responsibility without halting team delivery.

1. María (Auth Service Owner)

❌ curfew — failure
Curfew passed: 1 alert @maria has overdue dependency alerts in acme/backend: - jsonwebtoken (critical) due Day 7

SLA expired on Day 7. María's PR for a new feature is blocked until her service's debt is addressed.

2. Carlos (Billing Service Owner)

✅ curfew — success
Within curfew No overdue dependency alerts for @carlos.

10 minutes later, Carlos opens an urgent billing PR. His check is green. María's debt does not penalize him.

Resolution: María upgrades jsonwebtoken, the fix merges to the default branch, and Dependabot closes the alert. Upon synchronizing her PR, Curfew re-evaluates and switches immediately to green (Within curfew).

Engineering Honesty

Documented limitations

Curfew v0.1.0 is an experimental pilot. These operational constraints are intentionally public before seeking early adopters.

  • Approximate CODEOWNERS globs: Supports *, **, ? and leading-/ anchors. Negation (!) and escaped spaces are not yet supported.
  • No persistent queue: Webhooks are acknowledged immediately (202 Accepted). A crash or restart during processing can lose an in-flight evaluation.
  • Fail-open by design: If GitHub's API returns 5xx or fails transitorily, Curfew posts a passing check with a warning. A gate malfunction must never block an engineering team.

Help validate ownership attribution

We are looking for 2–3 engineering teams with active repositories and diverse CODEOWNERS configurations to test Curfew in informative mode (zero merge blocking).
