Narrative

A three-layer approach to dependency hygiene

Rather than introducing another scanning engine, Curfew provides the accountability layer that scanners lack.

Layer 1 · The Problem

Detection is not ownership

Scanners flood repos with alerts, but detection alone does not guarantee remediation. Without assigned owners and clear deadlines, backlogs expand until an audit or incident forces an emergency fire drill.

Layer 2 · The Mechanism

Ownership, SLAs & Checks

Curfew attributes dependency debt via CODEOWNERS, calculates severity SLAs with an installation floor, and evaluates responsibility at PR time. Zero database, zero background daemons.

Layer 3 · The Outcome

Hygiene as normal workflow

Security hygiene seamlessly integrates into the daily pull request lifecycle. María's overdue debt blocks María, Carlos's work flows unhindered, and dependency maintenance becomes continuous.

Use Cases

Built around real engineering situations

Six everyday scenarios where Curfew transforms informal security conventions into verifiable, low-friction rules.

Case 01

The developer with overdue alerts

A developer opens a pull request. Curfew detects they own a critical Dependabot alert that has exceeded its 7-day SLA.

Value: Dependency debt stops being invisible. It appears tied directly to a person and a deadline on the merge path.
Case 02

A team sharing component responsibility

CODEOWNERS attributes a manifest to @org/backend. If the PR author is a member of that team, Curfew evaluates the team's debt.

Value: Collective responsibility becomes a verifiable rule, not an informal agreement that gets forgotten.
Case 03

Maintaining hygiene across feature delivery

A pull request has flawless code and passing unit tests, but its author has overdue vulnerable dependencies in that repo.

Value: Curfew adds an automated security hygiene dimension to standard code review without adding reviewer fatigue.
Case 04

An organization needing to know who acts

A monorepo or large codebase contains dozens of manifests and multiple squads. CODEOWNERS maps alerts to owners.

Value: Eliminates ambiguity between detecting a vulnerability and knowing exactly who is responsible for resolving it.
Case 05

Security policy embedded into merge rules

The organization configures curfew as a Required Status Check in GitHub Branch Protection.

Value: Security policy transitions from an ignored suggestion to an automated, verifiable condition to integrate code.
Case 06

Gradual, low-friction adoption

The team installs Curfew in informative mode first, observing evaluation checks before making the check mandatory in branch protection.

Value: Progressive adoption with zero unexpected blockages or developer backlash.
Architecture

Ownership → SLA → GitHub Check

Curfew evaluates debt purely at pull request time without background polling, daemons, or persistent databases.

1

Attributes each alert via CODEOWNERS

Curfew matches open Dependabot alerts against the repository's .github/CODEOWNERS file to identify the user or team owning that manifest. If no rule matches, it falls back transparently to the last commit author who touched the manifest.

2

Enforces severity-based SLAs with an install floor

Default windows: Critical (7 days) · High (30 days) · Medium (90 days) · Low (exempt). The clock starts when the alert is published, but never before Curfew was installed — preventing historic debt from blocking day-one PRs.

3

Gates only the PR author's overdue debt

When a PR is opened or synced, Curfew publishes a GitHub Check. It fails only if the author owns overdue debt (directly or via team membership). With Required Status Checks, overdue debt blocks the merge.

Engineering Honesty

Documented limitations

Curfew is built with transparent operational boundaries.

  • Approximate CODEOWNERS globs: Supports *, **, ? and leading-/ anchors. Negation (!) and escaped spaces are not yet supported.
  • Fail-open by design: If GitHub's API returns 5xx or rate limits transitorily, Curfew posts a passing check with an explicit warning. A gate malfunction must never block deployment.
  • Serverless execution window: On Cloudflare Workers, evaluation runs in ctx.waitUntil() (30-second window). Suitable for medium repositories; large monorepos with hundreds of manifests will benefit from durable queues.
